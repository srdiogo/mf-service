# Reproducing a MiniFuse installation

Start with [INSTALL.md](INSTALL.md). The backend source kit generated by
`make arch-source` records its exact source revision and checksums. Keep its
`PKGBUILD`, source archive, `source-lock.json` and `SHA256SUMS` together. Retain
the built packages with their own SHA-256 manifest and `makepkg` build metadata.
The source archive includes the corresponding driver source and licenses.

## Desktop source baseline

[`distribution/desktop.lock.json`](../distribution/desktop.lock.json) pins the
approved GUI and plugin source used for the desktop baseline. Their source
archives are public:

```text
https://codeload.github.com/srdiogo/minifuse-control/tar.gz/c741b1885970f60ac9c11ad043cc377b9856635b
https://codeload.github.com/srdiogo/omarchy-minifuse/tar.gz/fbe846b2e01b0a202e0f9af3a1b633a8aa1bd4f1
```

Verify each downloaded archive against the lock before using it. A checksum
compares it to the reviewed profile; obtain the profile itself from a trusted
reviewed revision. These archives are sources, not automatic installers.

For an exact plugin checkout on a fresh machine, clone the public repository
into a new staging directory, check out the pinned full commit, validate it with
`omarchy plugin validate`, and move it to the unused
`$XDG_CONFIG_HOME/omarchy/plugins/srdiogo.minifuse` directory (default
`~/.config/omarchy/plugins/srdiogo.minifuse`). Run `omarchy-shell shell rescanPlugins`, then
enable/place it as documented. Do not overwrite an existing customized checkout.
A detached pinned checkout is a reproduction snapshot; intentionally return to
the supported release/branch before using the host's automatic Git updates.
Normal marketplace installation instead installs the currently published head.

Build the GUI from its reviewed native package recipe or install its wheel into
a dedicated user virtual environment as documented by that project. The pinned
GUI runtime has no dependency on Omarchy. The historical recipe inside that GUI
snapshot predates the visual refresh; use a reviewed updated recipe pinned to
the GUI commit above rather than rebuilding its older runtime source silently.
The optional desktop agent is not needed for mixer operation or logo events.

## Record before testing

Record the backend commit, core/service versions, native package checksums,
module hash, kernel/header versions, GUI/plugin commits, Python/Qt/Quickshell
versions and MiniFuse model. Keep personal paths, serials, host snapshots and
PCM out of a public report. Do not describe a source checksum as a measurement
of the installed binary or loaded module.

## Fresh-machine acceptance

1. Build the source kit on the target distribution and inspect package contents.
   Confirm that no CLI executable is included or needed and the driver package
   contains its source/license/access policy.
2. Install with matching kernel headers; record DKMS's successful build. Confirm
   installation alone did not start/enable a user service or create boot policy.
3. Explicitly activate driver/access and optional login startup. Run
   `minifuse-doctor` in the owning session. Confirm a single MF4 is usable and
   missing/unsupported devices leave controls unavailable.
4. Open each frontend. Confirm it reads current device state before enabling
   writes and that read-only meter events arrive. Compare physical switches
   without changing microphone power merely to test installation.
5. If controlled writes are needed, first save a private complete baseline and
   agree on safe speaker/microphone conditions. Exercise one bounded control,
   verify full readback and restore the baseline. Never auto-apply a preset at
   startup or use a test tone on an unprepared audio system.
6. Close/reopen clients, restart the user service and reconnect the device only
   when appropriate. Confirm fresh state, no operation replay and retained user
   presets. On Omarchy, confirm panel dismissal and optional GUI floating policy.
7. Reboot at a suitable time only after deliberately enabling boot/session
   integration. Verify the module and service on login, then test removal without
   deleting user evidence or changing the current device settings.

A local build, fixture test, staged installation and healthy existing session
cannot substitute for these fresh-machine checks. The driver import retains
historical MF4 evidence; it does not establish MF1/MF2 support, disconnect recovery,
new kernel compatibility or audio continuity on another machine.
